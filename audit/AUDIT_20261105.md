# Audit of 5 November 2026: what was fixed

The audit (kept outside the repository, in `../signet-audit`: `GENERAL.md`, `TX_CHANGING.md`,
`KEYEXPOSURE.md`, `EXTERNAL.md`, `AI_SLOP.md`) reviewed Signet `86b28df`, the Windows port and
the GTK port. This note records what changed in answer to it, so the findings can be read
against the code. Branch `claude@audit-20261105` in each repository.

## Security findings

| ID | Finding | Change |
| --- | --- | --- |
| G01 / T02 | The shielded wallet file's lock was process-local, so two processes could spend the same one-time WOTS+ key index. | `FileShieldedWalletStore` holds `tzel-<chain>.lock` with `lockf` under its in-process lock for every read and read-modify-write (5 s, then `ShieldedError.walletLocked`). Windows opens the same file with no sharing. `AuditFixTests.shieldedWalletFileIsLockedAgainstOtherProcesses` holds the lock from a second process. The recheck found the in-process lock keyed by the unresolved path, so two stores reaching the file through a symlinked parent took different locks (`lockf` is per process): the key is now the real path, as `TezosClientStore.LocalLocks` does, with `shieldedWalletFileLockIsSharedAcrossPathAliases` the regression. |
| G02 | The shielded master key is stored unencrypted, backups included, whatever the account's password. | Not changed: encrypting it would need the password for every background scan. The Shield and Shielded address sheets now say so before any tez are shielded or an address is handed out. Encryption with an unlock step remains a design decision for later. |
| G04 | The shipped Shadownet operator and rollup node are plain HTTP, the bearer token with them. | The deployment offers nothing else, so the Shielded settings sheet names any service reached over `http://` and what that means (`ShieldSettingsSheet.plainHTTP`). |
| G05 | The wallet file could be written larger than `PrivateFile.read` would read back (32 MB), after which it could not be loaded or backed up. | `PrivateFile.read(_:limit:)`; the shielded store reads and writes with one bound (128 MB) and refuses to replace the file with a larger one (`ShieldedError.walletTooLarge`). The recheck found the backup's snapshot and fingerprint still reading at 32 MB: every reader that takes a wallet file by name now uses `PrivateFile.readLimit(for:)`, which gives `tzel-<chain>.json` the store's bound (`backupsReadEveryWalletFileTheStoreAccepts`). Moving the scanned commitments out of the key file is still to do. |
| G06 / T03 | The GTK host's `signingCalls` lacked `sendTokenTransfer`, so NFT Transfer and Burn were refused before anything ran. | Added in `signet-gtk`. |
| G08 | A rollup head level near `Int.max` trapped in the fee computation; sums over untrusted figures were unchecked. | Levels must fit a non-negative `Int32` (`RollupState.level`, checked in `head()`, `cementedLevel()` and `requiredTxFee`); the pooled sum and the fee additions use reporting overflow. |
| G09 | New shielded keys and state waited for the next launch or an unrelated action to be backed up. | `backUp()` runs after the wallet or an address is made, after a pool is reserved and after an unshield or transfer record is written. |
| T01 | A withdrawal or transfer record was written only after the operator answered, and any error while polling removed it, freeing notes the operator might still spend. | The record, with the exact payload, is on file under a `local:` id before the operator is contacted; the operator's own refusal (the token, or a 4xx: `ShieldedError.rejected`) drops it, anything else keeps it (`WalletViewModel.submitShielded`). Once acknowledged the record takes the operator's id; only the operator marking it failed removes it. The sheets show "no acknowledgement received" with a Submit again button (`resubmitWithdrawal` / `resubmitTransfer` send the kept payload; the rollup refuses a repeated nullifier, so a copy that landed after all is reported as a duplicate) and keep Forget. A 408, 409, 425 or 429 is not a rejection (`RollupNodeService.isRejection`). |
| K01 / E01 / E02 | The bridge console serialised objects as they were, and the redactor missed UUID seeds and keys written as decimal bytes, so two dApp SDK log lines could carry its communication key. | The console formatter scrubs objects before `JSON.stringify` (fields named like secrets, byte containers, depth, width and node budget) and `redactedLine` stubs UUIDs to their first group and replaces runs of decimal bytes. `bridgeEchoObject` exercises it; the same change is in the Windows host. |
| E03 | The SDK forgets a pending request before the reply is delivered, so "Send reply again" could never succeed. | `octezConnectRespond` keeps the entry and puts it back when delivery fails (`test/audit-boundaries.cjs`). Upstream still deserves the fix. |
| G03, G07, K02, T04 | Windows: unbounded faucet work, inherited ACLs, the crash log, overlapping signing calls. | Windows: faucet limits and cancellation mirror Signet's; the crash log goes through the redactor line by line and rotates; signing calls run one at a time per bridge. Private ACLs for a custom directory (G07) are not done. |

## Behaviour-preserving changes from the anti-slop review

`FaucetService` uses `Hex.encode`; `checkApproved` reuses `checkApprovedReveal`; the preapply
predicate is `preapplyAccepted`, written out and tested; `NodeMonitor.probe(session:)` lets the
bounded-reader test hand in its session; the tzel vector checks fail instead of skipping when
`TZEL_VECTORS_REQUIRED=1` (bridge) or `SIGNET_TZEL_VECTORS_REQUIRED=1` (Swift) is set; Windows
`JSONValue` copies the collections it is given. The pin-aware port policy test and the Windows
collectible-refresh measurement were not done.

## Not done

Shielded master-key encryption (G02); separating scanned commitments from the key file (G05);
a Windows private DACL for user-chosen directories (G07); the upstream SDK fixes (E01 to E03).
