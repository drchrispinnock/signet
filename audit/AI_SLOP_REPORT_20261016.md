# Signet: code cleanup and verification review

The most useful cleanup would make safety tests harder to fool, remove unused wiring, and give repeated rules one definition. The code has also improved since the previous report: test-host construction uses memory storage, live/real-wallet tests require opt-in, and tokens/NFTs share a portfolio load. The recommendations below preserve wallet behavior, security checks, stored formats, errors, appearance and accessibility. No application speedup has been demonstrated.

Reviewed **2026-10-15** with the **anti-slop** skill: all eleven independent lenses completed, followed by a separate synthesis. Scope is handwritten Swift application/tests, JavaScript bridge/tests, and build/release configuration. The pinned application revision is **`be5ba28914abc8ed014d87808d8ccbb7214db504`**. A later concurrent commit, `1b7b60d`, changed README content; application/test/bridge files still matched the pinned snapshot at final verification. Existing roadmap and proposed shield documentation were not implementation work in this review.

This replaces the 2026-10-09 report. Findings **F02** and **F07** retain their earlier identities; F15 onward identify newly consolidated recommendations. Historical measurements and test results were not reused as current proof.

## Quantitative evidence

The inventory covers **164 handwritten files** and **25,799 physical lines**. Python **3.14.5** counted physical and nonblank lines using `splitlines()`/`strip()`; comment-inclusive counts are size proxies, not logical source lines or function complexity. Generated app JavaScript, generated project files, dependencies, lockfiles, assets and documentation were excluded.

For `WalletViewModel.swift` only, a separate exact count excludes blanks and standalone `//` comments. Inspection confirmed no block comments or multiline/raw strings in that file. Reproduction is `sum(bool(line.strip()) and not line.lstrip().startswith("//") for line in text.splitlines())`: **1,164 nonblank/noncomment lines**, versus **1,510 physical lines**. No whole-scope exact source-line total is claimed.

The skill's ten targets have these states:

1. **Cyclomatic complexity below 22/function — UNMEASURED.** No reliable scoped function measurement.
2. **Cognitive complexity below 22/function — UNMEASURED.** No reliable scoped measurement.
3. **Halstead Difficulty below 80/function — UNMEASURED.** No appropriate per-function result.
4. **Every file below 500 nonblank/noncomment lines — FAIL.** WalletViewModel alone is a measured counterexample. Size indicates an investigation point, not an instruction to scatter its methods.
5. **CRAP score below 25/function — UNMEASURED.** Matching function complexity and coverage are unavailable.
6. **Complete mutation run with no actionable survivors/uncovered mutants — UNMEASURED.** No complete run.
7. **No confirmed dead code — FAIL.** F16/F22 provide specific confirmed unused internal code. The inventory is not exhaustive.
8. **No confirmed redundant responsibility — FAIL.** F15's identical signer factories and F07's duplicated menu are confirmed counterexamples; this is not a whole-scope duplication percentage.
9. **No unjustified explicit/inferred `any` — UNMEASURED.** Swift protocol existentials are constrained and are not equivalent to unrestricted TypeScript `any`; no complete inferred-type assessment was established.
10. **TypeScript `unknown` only at narrowed boundaries — NOT APPLICABLE.** Swift, JavaScript and shell do not use that TypeScript type. Variables named `unknown` are unrelated.

These threshold results do not establish that the whole application is poorly designed. No broad analyzer installation, metric-driven file splitting, or general tooling project is endorsed.

## Verification and scope limits

**Matching-source checks that passed:**

- All five offline bridge harnesses via `npm test`, run from a temporary copy with the pinned shipped bundle and installed locked dependencies. An initial missing-resource error in that temporary setup was corrected before the passing run.
- Isolated `xcodegen generate` and `xcodebuild ... build-for-testing`, using copied local Sparkle inputs, Swift 6 and complete strict concurrency. Original build configuration and source files were not edited.
- Hosted `test-without-building` for `SendOutcomeTests` and `SigningExportsTests`: **four tests in two suites passed**, with live-network and real-wallet opt-ins disabled. The previous review's LaunchServices failure is not treated as the current result.
- A standalone Node **v26.11.1** check of all four read-only factory bodies: identity, no-secret and signing-refusal assertions passed. The exact scanner counterexamples were also exercised with the pinned Swift scanner in isolation; its missed cases are verification findings, not production exploit demonstrations.

These checks establish a baseline. None verifies a refactor that has not yet been implemented. The full hosted suite, manual menu/UI comparison, physical Ledger, live relay/chain/Etherlink operations and before/after performance comparisons were not run. No personal wallet or production log was read. Any cleanup must retain signing-policy classification, exact approved bytes/limits, outcome journaling, generation checks, wallet locks, private-file policy and network/HTTP budgets.

The earlier report's eager disk-backed test construction and private peer map are no longer current findings. Current test-host setup is in-memory, default bridge storage is in-memory with no log root, live/real-wallet traits require opt-in, and the dashboard uses a shared portfolio result. The remaining recommendations above were independently checked against this source revision.
